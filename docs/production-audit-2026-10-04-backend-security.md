## Authentication and OAuth assessment

The product intentionally supports administrator-issued employee accounts, not open signup. Password reset is an administrator-issued single-use invitation; there is no public forgot-password endpoint, separate email-verification state or third-party OAuth login/account linking. Invitation acceptance proves access to the delivered capability but live mail delivery remains UNVERIFIED. Account bootstrap is a local private password prompt.

Passwords use Django configured validators/hashers. Login is bounded by a shared global/per-email database throttle. Sessions use high-entropy opaque tokens; only SHA-256 hashes persist. Server access checks include expiry, active/deleted account state and setup gates. Logout revokes the current session; password changes and administrative status/reset changes revoke employee sessions and MCP connections. The new races above close stale authorization at critical password/session writes.

MCP is a separate OAuth authorization server for external assistant capabilities, not employee login. It requires S256 PKCE, exact registered callbacks, exact resource URL, short-lived opaque authorization handles/codes, live employee consent, hashed access/refresh tokens and refresh rotation. Code and refresh-token replay revoke the family after matching client/proof prerequisites. Invalid authorization requests do not redirect to submitted URIs; registration never fetches caller metadata URLs. Loopback HTTP callbacks are an explicit desktop-client exception; public HTTP MCP hosting is rejected. Browser consent returns the OAuth callback code, not provider secrets. Old-code/expired-token/state/foreign-client/revocation/denial/malformed input regressions are present.

The OAuth client's state is carried unchanged to its registered callback; validation of that state against the initiating external client's browser belongs to the external client. A genuine Claude/ChatGPT interoperability test was **UNVERIFIED**. No MFA implementation exists in assigned account code; deciding whether this private employee deployment requires MFA/SSO is an operational/product security requirement, not claimed satisfied by password tests.

## Authorization and employee isolation assessment

Every private assigned API enters the existing service-token plus live-session `access()` decorator. It derives `request.actor` and private database routing from the server-owned AccountProfile UUID, never browser user/workspace/account identifiers. Admin routes require the live `is_staff` role; employee creation cannot grant a submitted administrator role, and self-deactivation/last-active-admin protections remain.

Canonical contacts/mailboxes/campaigns are queried inside the employee's physical SQLite database. Drafts/Chat records add actor predicates where applicable. MCP operation lookup and idempotency bind both actor and connection. The strict typed MCP catalog cannot select shell, raw SQL, arbitrary HTTP, admin routes, credential setters or browser-supplied approval controls. Direct external assistant actions generate a portal review and execute only the one approved capability. Runtime Chat and the manual Workspace share domain handlers and persisted records.

Workers receive server-derived actor/workspace/control database identities and scrub provider exports. `assert_worker_access()` revalidates the control account; MCP adds connection revocation checks. Chat execution, discovery/provider/transport sinks check cancellation, deadlines and relevant approved snapshots. Approval consumption occurs before the external effect; uncertain work is not blindly repeated. Real-file scenarios use two employees with overlapping IDs, forged workspace selectors, foreign draft/conversation/run IDs, revoked workers, credential mocks and actual private DB routing. Cross-employee private reads/provider calls were blocked in those scenarios. This is not a claim that a local OS administrator cannot read employee files.

## API, input, storage, cache and error assessment

Assigned public OAuth/MCP input is bounded by content type/body lengths, strict object/schema shapes, exact callbacks/resources, protocol/Origin rules and database-backed throttles. Assigned private APIs use bounded JSON, pagination/record limits and explicit methods. No raw SQL/eval/shell-selected input path was found. Subprocess module/argv, database root and account UUID come from server configuration/records. Canonical context fields and Workspace navigation paths are allowlisted. Provider endpoints remain approved-host/TLS/public-address/pinned-connection guarded through the existing shared transports; their full implementation is audited by the domain/integration agent.

Authenticated responses use no-store; SSE reacquires the employee database scope after decorator exit and rechecks session state on every snapshot. A per-actor stream lease bounds simultaneous streams. Backend CORS uses configured explicit origins, not a wildcard. APIs do not use cookie auth; Next.js cookie/origin/CSRF behavior and security headers are audited separately by frontend/root. Django's HTML 404/405/error responses and global headers depend on root's configured middleware.

Employee backups require a live workspace session, explicit POST confirmation, a server-derived file path, a nonsymlink existing DB and a 512 MiB limit. SQLite's read-only backup API includes committed WAL state, converts to a self-contained journal format and has a 10-second progress deadline. Real two-workspace scenarios assert content/authorization isolation and integrity. It exports one employee database, not a full-server restore. No upload endpoint or public object-storage integration exists in assigned code.

Provider errors on probes, workers, MCP transport and model runs return generic employee-facing failures without exception details. Raw model/tool text is redacted by current configured secret values and recognized key prefixes. This cannot certify historic logs contain no unknown/rotated credentials or personal data. Configured credentials stay server-side/encrypted; production key management, file permissions and historic-log retention remain deployment evidence requirements.

## Database and performance assessment

Reviewed account migrations are additive except normal foreign-key cascades on intentional database-level account removal (the application itself soft-deletes). Opaque token hashes are unique, expiry indexes exist, AccountProfile is a one-to-one user relation, and invitation consumption/refresh rotation use guarded transactional updates. Production SQLite uses IMMEDIATE transactions; the short critical write checks intentionally depend on that serialization. No production data was deleted. Global control/employee migration execution and restore rehearsal belong to the parent/domain reports.

Private reads are bounded, but counted searches, high offsets and SSE's 4 snapshots/second can still be expensive at large scale. The assigned module review found no evidence for production concurrency/latency capacity. The new readiness endpoint verifies only the control database and migration records; filesystem write capacity, every employee database, scheduler heartbeat and external services need separate monitoring. It does not execute a migration, real provider request or write probe.
